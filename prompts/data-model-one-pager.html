Ballpark — Data Model

Tables, relationships, audit pattern, and the three-schema environment split.

Core entity relationships

Item composition — buildup tree BUILDUP-01 · dormant

  • One recursive node. A line nests under another via project_items.parent_id (self-FK). The buildup is a tree — no separate "component" table.
  • The tree is pure cost. Every node rolls up cost; the client charge sits above the roll-up; margin is the gap. A single project-level margin (the existing EstimateBreakdown cascade), not per-node.
  • Authorship = the authority / visibility line — who owns a node (agent vs supplier) drives what each side may see and edit. (The stamp is created_by; there is no added_by column.)
  • Private-cost boundary. Leaf costs never reach a client surface — an RP-11-shaped rule (one predicate, enforced at every place a line renders). The v2.65 fix that filters the explore pre-load to editable() is the same one-place-predicate discipline.
  • Schema impact ≈ one column. New columns are dormant + additive (all NULL, unwired): items.kind, project_items.kind (VARCHAR 20), project_items.parent_id (UUID self-FK) + index ix_project_items_parent. items.parent_item_id / derived_from_id are data-empty (0 / 346) but writable lineage fields today — not a free composition slot.

Shipped dev-only v2.62–v2.65 (architect-audited 2026-08-25, no blockers). Not yet wired — the columns are placeholders until the components / time-&-materials build lands. Design record: docs/PROGRESS.md.

Universal patterns

  • Every business table has 6 audit columns: created_at, created_by, updated_at, updated_by, deleted_at, deleted_by
  • Soft-delete via deleted_at IS NULL filter on every read. Hard-delete is forbidden on entity tables (trigger raises).
  • Junction tables exempt from soft-delete — they hard-delete (e.g. cart item removed = row gone).
  • Active flag co-exists with soft-delete on items: is_active (publish toggle) + deleted_at (soft-delete).
  • UUIDs generated via gen_random_uuid() (PG13+ built-in, schema-portable).
  • Audit trigger stamps updated_by from current_user_id() session var.
  • Reports gate on parent chain — not the child's own flag (a project_item is "live" if the project is, not just if it's not deleted).

Key tables

orgsAgencies, suppliers, Ballpark itself. org_type drives behaviour.
usersAuth identity. Each user belongs to N orgs via user_orgs.
clientsAn agency's customers (e.g. "Nike"). Tied to the agency org.
projectsAn event. Belongs to one client. Has many cart items, estimates, messages.
categoriesMarketplace taxonomy. Same names across orgs.
itemsA supplier's catalogue entry. Belongs to one supplier org + one category.
project_itemsThe cart — project ↔ item junction. Project-level, fans out per supplier on checkout. Also the buildup tree: parent_id nests cost-part children under a line, kind classifies the node dormant
messagesConversation thread, one per (project, supplier). Author + body + status.
message_itemsItems being discussed in a message. Status pill lives here.
message_item_decisionsAppend-only audit per item: accept / decline / price change / qty change.
balls_transactionsCredit ledger. Append-only. balance = SUM(amount).
estimates · estimate_itemsCost roll-ups per project.

Three-schema environment split

One Supabase Postgres instance, three logical environments via schemas:

publicLocal dev. Free to break.
previewTracks dev branch. Internal QA.
masterTracks master branch. Customer-facing.

The API picks its schema via APP_SCHEMA env var at boot. Same code, different data set per environment.

Migrations

  • Single source of truth: server/src/db/migrate-schemas.js
  • Every column / table / ALTER writes to all three schemas explicitly
  • Legacy migrate.js is deprecated — don't add to it
  • Run order: public → preview → master; rollouts are gated per environment
  • Historical migrations live under migrate-v1.*.js as a paper trail; canonical truth is the schemas file
  • Phase 4 guard (v1.66e6) blocks accidental hard-delete on entity tables via PG trigger
