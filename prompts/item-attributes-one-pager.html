Ballpark — Item Attributes

Supplier-entered "additional details" on marketplace items — admin-curated, codelist-driven, profile-templated. Rides entirely on existing ref-codelist machinery: no new tables, no new admin UI.

How it flows — admin defines · category templates · supplier fills · item shows

Attribute model — one codelist, four value types

Each item_attribute value (a ballpark-type list, so admins add values, suppliers never can) carries its display type in the existing meta JSONB — no schema change.

Rides on existing machinery

  • Attributes + profiles + option sets are all shared.reference_codelists / ..._values rows — curated in the admin codelist screen you already have.
  • Type + options + membership live in the values' existing meta JSONB. No new columns, no migration on the codelist tables.
  • Only ballpark-type lists are admin-extendable (locked rule 1, codelist.service.js) — this is exactly the proliferation control we want.
  • Values land in items.attributes — the JSONB bag that already exists (currently {} on every item; dormant since BUILDUP).
  • Category → profile reuses the existing categories admin screen (one profile code on the category).

Storage & rendering

  • Ordered array in items.attributes so display order is preserved and duplicates are impossible-by-choice.
  • List-type stores the code, not the label — label resolves from the source codelist at render, so an admin rename updates every item.
  • Label + type resolve from the codelist at display, same pattern as status pills — the bag holds keys + raw values only.
  • Graceful empty — an item with [] shows no "Additional details" block.
items.attributes = [ { "key": "derig", "value": "We deinstall within 48 hrs…" }, { "key": "pieces", "value": 100 }, { "key": "fire", "value": "flame_resistant" } ]

Profiles — fixed sets, per category

  • item_attribute_profile codelist; each value's meta.attributes = ordered member attribute codes.
  • Assigned to a category (Catering → Profile 1). Adding an item in that category auto-renders that fixed set.
  • Purpose: make the common fields appear automatically — less hunting, consistent data across suppliers.
  • "More" escape hatch: supplier can still add any other existing attribute beyond the profile.
  • Category-level for now; per-item override deferred.

Supplier flow

  • Fill the normal fields (name, cost, unit…).
  • Profile's fixed attributes appear below, pre-labelled, with the right input per type.
  • Fields are optional — leave blank / remove any that don't apply.
  • + More → pick any other existing attribute + enter a value.
  • Saves to items.attributes; shows on the item view (and later the quote) automatically.

Decisions locked

  • Admin-only attribute creation; suppliers pick, never invent.
  • attributes = display-only spec sheet (prose / enums). Distinct from tags = the filterable taxonomy facets.
  • Profile at category level; item override later.
  • Profile fields optional + removable per item.
  • Profiles and ad-hoc "More" coexist.

Build phases

Phase 1 firstitem_attribute codelist (with meta.value_type incl. list) + supplier "Additional details" editor ("More" picker, typed inputs) + read-only display block.
Phase 2 nextitem_attribute_profile codelist + category→profile assignment + auto-prefill of the fixed set.

Only genuinely new code is supplier-side (editor + display). Everything admin does is data entry in screens that already exist.

For review: (1) storing the ordered array in items.attributes replaces the current {} shape — safe, since the bag is empty on every item today, but confirm nothing reads it as an object. (2) List-type stores the code and resolves the label at render — consistent with the codelist pattern; the alternative (store label) trades rename-safety for read simplicity. (3) Category→profile is a single profile code on the category; multi-profile / per-item override intentionally deferred. Design record: [[project_item_attributes_arc]] memory + this page.
