Security Posture · Multi-tenant isolation

Ballpark Security Posture

Tenant isolation is enforced by the database, not by application discipline. This is the audit of that guarantee — the model, the findings it closed, and the tests that prove it.

Spec pV2-SECURITY-RLS-01 Epic EP-00020 Enforcement live on dev As of 2026-09-20

The guarantee: a developer forgetting a WHERE org_id = … clause cannot leak another tenant's data. Org identity comes from a server-signed JWT and is re-proven on every request; the application connects to Postgres as a non-owner role subject to row-level security, so isolation holds at the database even when a query is wrong. Per-query discipline is the convenience layer; the database is the backstop.

01 How isolation is enforced

Six mechanisms, each doing one job. Together they move tenant isolation from "every query remembers" to "the database refuses."

Non-owner app role

The app connects as web_app_user (not the schema owner), so RLS applies to it. Migrations use a separate owner connection.

Request-scoped identity

A request-pinned client sets app.current_org_id from the verified JWT once per request, reset on release — no cross-request leak.

Split read / write policies

Catalogue reads cross-org (approved only); writes are hard-isolated to the owning org. Projects & messages are two-party (agency + supplier).

Safe cross-org display

An orgs_public view exposes supplier name/logo without PII; a counterparty policy lets the two parties on a project line see each other's org.

Auth bootstrap

Login and onboarding write before a tenant context exists, so they run through a dedicated owner pool — the only elevated path, and a narrow one.

Coverage is proven, not assumed

A test asserts every table the app role can touch carries a policy — a missed table fails the build, so nothing ships open.

04 Verification

Isolation is machine-checked, not eyeballed — the tests run as the restricted role and assert the matrix above.

Persona suite — 77 / 77

Supplier, agency, admin, and no-context, each asserted against the access matrix as web_app_user.

Coverage guard

Every base table granted to the app role must carry ≥1 policy, or the build fails. Caught a missing table on day one.

Auth-bootstrap test

Proves a users insert is denied under the restricted role and succeeds only through the owner pool.

No-context deny

A request with no tenant context sees only approved public rows and can write nothing.
