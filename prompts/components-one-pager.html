Two composition trees

Same recursive shape, two layers — the catalogue is the menu, the project line is the chosen buildup.

  • Catalogue template — the supplier defines, once, what an item is made of (its options, variant set, T&M breakdown). Children are real items rows, kind-typed. STORAGE OPEN items.parent_item_id already means lineage ("variant of / born from") and is written today — composition needs its own FK (e.g. composed_under_id) or the item_components join, not that column.
  • Project instance — project_items.parent_id When an agent drops the parent into a quote, the chosen subtree instantiates here as project lines.
  • Instantiation connects them — adding the parent copies mandatory components + the picked variant + chosen options down into project_items.
  • Margin lives only at the project layer. The catalogue carries cost/pricing rules; the project line resolves them into a quote. The single project-level margin cascade (server computeEstimate in estimate.js; client renders it as EstimateBreakdown) never leaks up into the catalogue definition.

Authoring — in the context of an item

  • Go to an item → supplier clicks Add options / estimate / variant. The item you're on is the parent (context sets it — no parent picker); the button sets the kind.
  • Item-scoped for now. Components are created + reused only under their parent item. No standalone existence, no browse surface yet.
  • Later: a components manager = a copy of the marketplace on a new route, the same catalogue engine (catalogue-layout + MarketplaceStore) filtered to kind = component. A filter and a route, not a rebuild.
  • The explore add-lines dialog is the primitive the child-authoring modes (options / estimate / variant) reuse.

Pricing basis & the open fork

  • Each node carries price_basis ∈ (flat | percent | per_primary_unit) + an explicit operand (what it counts / is a % of — parent qty, parent cost, subtree, project).
  • Flat & per-unit children are clean cost nodes — they roll up, margin sits above, the pure-cost tree holds.
  • The % child — proposed resolution. 10% of cost → it's a tree node (rolls up, single cascade survives). A 10% client fee on charge → not a tree node at all: it belongs at the project cascade layer beside margin/VAT in estimate.js, so "tree is pure cost" holds by construction. PROPOSED — pending lock
  • Private-cost boundary (RP-11). Component / T&M leaf costs never reach a client surface — one predicate, enforced everywhere a line renders, keyed off kind plus authorship (created_by, the audit stamp — there is no added_by column; add a purpose-built owner column only if creator ≠ owner).

Schema footprint — what's there, what's needed now, what's deferred

  • Live (inbox buildup): project_items.parent_id (UUID self-FK) + index ix_project_items_parent and project_items.kind (VARCHAR 20) — written + read by saveComponents / listComponents (see the correction at the top). items.kind backs the catalogue listing filter. Dormant: items.parent_item_id / derived_from_id are data-empty (0 / 346) but writable lineage fields today (item create/update) — not a free slot for composition (see "Catalogue template" above).
  • The one guard needed at authoring time: items.kind earns a second job — catalogue visibility. The marketplace / store listing must exclude components (kind = 'primary' OR kind IS NULL) the same commit components can be created, or a child fridge pops up as a standalone card.
  • Deferred — forced only if a child stores catalogue provenance in an unscoped item_id (agent-owned, supplier_org_id NULL): then relax uq_project_items_canonical to key on (project_id, item_id, parent_id). If provenance lives in a separate column (item_id stays NULL) or children are supplier-scoped, they dodge the index and no relax is needed. PROVENANCE OPEN
  • Deferred — components library: the marketplace-copy manager, plus a item_components join if one component is reused across many items (the single parent_item_id FK is a deliberate one-parent floor, not the library's shape).
