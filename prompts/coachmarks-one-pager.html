How a coachmark reaches the screen

Tracking: bubbles are code-defined and auto-register (upsert) their row on first render — the table is then where admins edit the copy + toggle active (no add / delete).

The primitive — <app-coachmark> BUILT

One presentation component; the pink bubble per spec. client-v2/.../shared/coachmark/coachmark.component.ts.

  • Anatomy: white --color-surface card, 18rem wide, --theme-accent border + a 2px ring + pink glow shadow, rounded 1rem, a rotated-square tail merging into the card.
  • Inputs: key (required — the dismissal id) · tail ('up'/'down', default up). Body via <ng-content>. Output: dismissed.
  • Foot: a "Don't show again" checkbox (left) + an "Okay" gradient button (right).
  • Token: rides --theme-accent throughout (the old --primary mapping) — themes per org.
  • Reusable: drop it anywhere, pass copy + tail side. First mount target: the Ballpark Cost tab.

Behaviour — Okay vs Don't-show-again

  • Shows on mount unless previously suppressed. Renders nothing when suppressed.
  • "Okay" = dismiss this mount only — it may show again next visit.
  • "Don't show again" + Okay = never again on this browser: persists bp-coachmark:<key> = 1 in localStorage (try/catch for private mode).
  • Per-browser, not per-account (localStorage). A server-side per-user flag (follows the account across devices) is the deliberate later option; starting with localStorage.
  • First instance copy: "Here is your ballpark cost. Feel free to remove anything and add elements from the marketplace." (tail up, at the tab).

Data model — coachmarks table PLANNED

Global platform config in migrate-schemas.js (all 3 schemas), no org scoping — like codelists. Rows aren't authored in admin: code-defined coachmarks auto-register (upsert) their row on first render — that's the "tracking". The table then holds the admin-editable copy + active flag.

pagewhich surface (e.g. ballpark-cost)
namecoachmark id on that page (e.g. intro)
descriptionthe coachmark body copy
infoextra help text — a "more info" layer FUTURE · out of scope
designnotes on the design + planned / design enhancements for this surface FUTURE · out of scope
tailup / down (default up)
is_activeshow / hide (default true)
sort_orderorder when a page has several

Unique on (page, name) · + audit columns. Client key = page:name. First render seeds description from the code default; an admin edit then wins. info + design are a future extension — nullable additive columns, out of scope for the first build.

Server + admin PLANNED

  • Read — GET /api/coachmarks?page=…, open to any authenticated user (the app fetches what to show).
  • Register — an idempotent upsert on first render (any authed user): inserts the code-declared (page, name, default copy, tail) if absent, no-op if present. Not an admin action.
  • Edit — PATCH /api/coachmarks/:id behind ballparkAdminGuard (admin.cross_org_view), limited to description + is_active. No create, no delete — the code owns which coachmarks exist.
  • Service — coachmarks.service.js holds the SQL; routes stay thin (ENGINEERING Rule).
  • Admin surface — a new /settings/coachmarks (ballparkAdminGuard) + CoachmarksSettingsComponent: a page · name · description · active table where admins edit copy + toggle active only (no add/delete). Mirrors codelists-settings' edit affordances; linked from the account-menu admin links (beside Page settings / Early access).
  • Client — CoachmarkService fetches by page (and registers on first render); a tab requests page='ballpark-cost' and renders each active row via <app-coachmark>.
